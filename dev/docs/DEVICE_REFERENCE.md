# Basilisk V3 有线版 — 设备知识档案

> 这份文档的目标：让**人**和 **AI** 都能快速、准确地了解"我们到底在控制一块什么鼠标"。
> 它把散落在 `PROTOCOL.md`（协议实测）、`PLAN.md`（踩坑记录）、源码和 CLI 里的设备事实
> 收敛成一份单一参考源。写新功能、排查问题、回答"这个鼠标能不能……"之前，先看这里。
>
> 目标设备：**Razer Basilisk V3 有线版**，`VID_1532 / PID_0099`，实测固件 v1.2。
> 最后核对：2026-11-24。

## 0. 证据等级（全文通用）

文中每条事实都标了等级，避免"文档这么写"和"本机真的验证过"混为一谈：

| 等级 | 含义 |
|---|---|
| **A** | 本机实机验证：真发报文、读回比对、或物理按键确认 |
| **B** | 开源逆向文档（openrazer / razerqdhid 等）记载，本机行为与之相符 |
| **C** | 逆向文档记载，本机未单独验证 |
| **推断** | 由实测现象推出的结论，非设备直接回报 |

给 AI 的规则：**回答设备能力时优先引用 A 级条目；C 级与推断要明确说明"未在本机验证"。**

## 1. 设备速览（先建立整体印象）

| 项目 | 值 |
|---|---|
| 名称 | Razer Basilisk V3 有线版（Basilisk V3 Wired） |
| USB ID | `VID 0x1532` / `PID 0x0099` |
| 固件 | 1.2.0（A，读 `0x00 0x81` 得到 `01 02 00 00`） |
| 连接 | USB 有线，无需专有驱动 |
| 控制通道 | HID 厂商控制口 **MI_03**，usage page `0xFF00`，90 字节 feature report（A） |
| 板载槽位 | 5 个可持久化配置槽 + 1 个临时层 p0（direct profile） |
| 可板载持久化的能力 | 按键绑定、板载宏、灯效（静态/光谱/波浪）、DPI 档位、回报率、滚轮三项 |
| 不落盘的能力 | p0 的即时改动、DPI 的即时写入、CUSTOM 逐颗灯效、软件灯带预览 |
| 官方软件 | 可完全脱离 Synapse；本项目已把相关雷蛇服务设为禁用（`Start=4`） |

一句话概括：**鼠标内部有一块 Flash，存着 5 套配置（槽）；上电后固件按当前激活槽的配置自己工作，
不需要电脑装任何软件。所有"控制"本质上就是读写这块 Flash 和它的 RAM 工作副本（p0）。**

## 2. USB 接口结构

设备暴露 4 个 HID 接口（A）：

| 接口 | 用途 | 本项目是否使用 |
|---|---|---|
| MI_00 | 标准鼠标（endpoint 1） | 否，系统直接驱动 |
| MI_01 | 键盘 / consumer / system（endpoint 2） | 否；仅在 **driver mode** 下由厂商软件占用 |
| MI_02 | boot 键盘（endpoint 3） | 否 |
| **MI_03** | **厂商控制口**，usage page `0xFF00` / usage `0x01` | **是，唯一通道** |

打开方式：`CreateFileW` 打开 `\\?\hid#vid_1532&pid_0099&mi_03#...`，
用 `HidD_SetFeature` / `HidD_GetFeature` 读写。**Windows 自带 HID 驱动即可**，
不需要雷蛇驱动、不需要内核驱动。

> 关键认识：MI_01 这个"键盘接口"的存在，正是 driver mode 的硬件基础——切到该模式后
> 鼠标不再自己发键，而是通过它把按键交给电脑软件处理。详见 §3。

## 3. 设备模式（mode）—— 最容易被误解的概念

### 3.1 模式与槽位是两回事

给人和 AI 的第一条提醒：**"模式"（mode）和"槽位"（profile/slot）是两个正交的概念。**

- **模式**决定"由谁解释按键"：鼠标固件自己（normal），还是电脑软件（driver）。
- **槽位**是 5 套可切换的具体配置（按键/宏/灯/DPI 各一份），底部 Profile 键切的是它。

设备模式是一个字节，读命令 `0x00 0x84`，写命令 `0x00 0x04`（A）：

> **产品术语对照**：上位机界面把协议模式映射成更好懂的说法——
> `normal (0)` 显示为「**离线模式**」，`driver (3)` 显示为「**在线模式**」。
> 协议值不变，只是显示文案。但要注意：RazerMate 的「在线模式」功能（无限虚拟槽）
> 底层仍运行在 `normal (0)` 下，靠 p0 实现；真正的 `driver (3)` 只在写 DPI 时短暂进入。
> 详见 §3.4。

| 值 | 名称 | 界面显示 | 说明 | 本机验证 |
|---|---|---|---|---|
| `0` | normal | 离线模式 | 固件自己读 Flash 配置发键，**板载宏/绑定生效** | A |
| `1` | bootloader | 引导模式 | 固件升级用 | 仅文档记载，未测 |
| `2` | test | 测试模式 | 工厂测试 | 仅文档记载，未测 |
| `3` | driver | 在线模式 | MI_01 激活，**板载绑定与宏全部失效**，由软件接管 | A（切 3 再切 0 已实测） |

### 3.2 离线模式 vs 在线模式（协议层 normal vs driver）

**正常模式 (0)**：这是日常应处的状态。鼠标固件自己读 Flash 里的配置执行——按键绑定、
板载宏、灯效、DPI 全部生效，**不装 Synapse 也能完全正常工作**。这正是 RazerMate 方案
成立的前提：写入配置后让设备留在正常模式，脱机也生效。

**驱动模式 (3)**：Synapse 运行时使用的模式。MI_01 厂商 report 通道被激活，板载绑定和宏
**全部失效**，按键改由电脑软件接管转发。它在本项目里只有一个用途：**写 DPI 必须在此模式下**
（正常模式下写 DPI 会"返回 OK 但值不变"的静默失败，见 §8）。

> ⚠️ 本项目最危险的点：任何异常退出若把设备留在 driver mode，用户会感觉"宏全坏了"。
> 因此 `razer-core` 的 `set_dpi()` 采用"读原模式 → 切 3 → 写 → 读回校验 → 切回原模式 →
> 失败回滚"的完整流程，`razerctl normal` 是专门的修复命令，GUI 启动时也会自检模式。

另有一个已实测的副作用：**切到 driver 再切回来，生效槽会被重置为 1 号槽。**
`set_dpi()` 因此还会记住并还原原槽位（A）。

### 3.3 常用的模式命令

```
razerctl mode            # 读当前模式（"mode 0:0 (normal)"）
razerctl normal          # 从 driver 切回 normal，修复"宏不响应"
```

### 3.4 RazerMate 的「在线模式」= p0 虚拟槽（重要）

这是本项目对"在线模式"的产品化定义，**与协议层的 driver mode 刻意区分**：

- **离线模式**：只用板载 5 个槽，宏由固件执行，不装后台也能用；
- **在线模式**：虚拟槽数量不限，按前台程序自动切换整套按键 / 灯效 / DPI，
  写入 p0（临时工作层），**零 Flash 磨损**。完整配置存在磁盘
  `%LOCALAPPDATA%\RazerMate\vslots\`，索引在 `vslots.conf`。

**为什么不用真正的 driver mode 做在线模式**：协议实测 driver(3) 下板载宏全部失效，
要让它生效必须新增"软件按键转发"（常驻读 HID 输入、拦截按键、由软件合成宏），
这与"后台尽可能省内存"的目标直接冲突，工程量和风险都高一个量级。
p0 方案下宏仍由固件执行，底层保持 normal(0)，既满足"无限槽 + 按应用切宏 + 更多灯效"，
又最省内存。

**后台内存优化的关键设计**：
- agent 常驻内存的只有虚拟槽**索引**（每个槽仅 id / 名字 / exe 规则），
  100 个槽实测仅增加约 32 KB 私有内存；
- 槽的**完整配置**（按键、灯效、亮度、DPI）只在命中那一刻读进来、套用完立即释放，
  绝不让无限个槽的全文常驻；
- 套用走差量：值与当前相同就跳过写入，减少 HID 往返，也避免不必要的模式切换。

agent 命令：`--vslots` 列虚拟槽、`--vsapply <id>` 手动套用；
IPC：`VSLIST` / `VSAPPLY` / `VSRELOAD` / `VSSTATUS`。

## 4. 槽位（profile / slot）与 p0

### 4.1 5 个板载槽 + 1 个临时层

`0x05` 类命令管理槽位：总数 5、启用数 5、启用列表 `[1,2,3,4,5]`（A）。
Profile `1..5` 是**板载槽**，内容存在 Flash 里，断电保留；底部 Profile 键切的就是它们。

**Profile 0 是特殊的 direct profile（"直接配置"）**，协议文档原话：
> 编号为 0 的话，设置立即生效，鼠标断电就会重置，不会保存到板载内存中。

本机六组实验确认（A）：

| 属性 | p0 的实测行为 |
|---|---|
| 读 | 返回内容**恒等于当前激活槽** |
| 写按键 / 灯效 / 亮度 / DPI | 立即生效 |
| 写 Flash | **零写入**（available / recycled 前后完全一致） |
| 对板载槽的影响 | **无**，写 p0 后 slot 1..5 内容不变 |
| 切槽 | p0 被目标槽的 Flash 内容**覆盖** |
| 物理按键触发生效 | **是**（按 p0 绑定的键成功播放宏，实验 G） |
| 断电 | 重置为激活槽内容 |

**结论（推断）**：p0 是"当前生效配置的工作副本"，是纯 RAM 层。
写 p0 = 立即生效 + 零磨损 + 不影响板载槽，但任何切槽都会丢弃它。

> ⚠️ **顺序铁律（2026-11-24 v2 真机复现）**：`set_dpi()` 会切到 driver mode 再切回，
> 设备随之重置生效槽，函数内部为还原槽位会调 `set_active_profile()` —— 这等同于切槽，
> **会用目标板载槽的 Flash 内容覆盖整个 p0**。所以 `apply_virtual_slot()` 必须按
> `DPI → 回报率 → 灯效 → 亮度 → 按键绑定` 执行，按键绑定永远放最后。
> 反序时的现象极具迷惑性：报告显示「按键 N 项写入成功」，逐条读回却是板载槽的旧值。
这正是 RazerMate"虚拟槽"方案的基石——切换虚拟槽就是往 p0 写一套配置，不产生 Flash 写入，
用户按物理 Profile 键时硬件自然接管。

> 给 AI：不要把 p0 当成持久层；不要缓存 p0 状态跨越切槽操作。

### 4.2 槽位相关命令

| 操作 | cls/cmd | size | 参数 / 响应 |
|---|---|---|---|
| 槽总数 | `0x05 0x8A` | 1 | → `05` |
| 启用数 | `0x05 0x80` | 1 | → `05` |
| 启用列表 | `0x05 0x81` | 6 | → `[总数, id1..id5]` |
| 激活槽 | `0x05 0x04` | 1 | 写 profile / 读发 `0x00` → profile |

## 5. 按键与绑定

### 5.1 按键 ID（物理键）—— 实测表（A）

| 按键 | ID | 按键 | ID |
|---|---|---|---|
| left 左键 | 1 | dpi（DPI 键） | **96** |
| right 右键 | 2 | clutch（狙击键） | **15** |
| middle 中键 | 3 | profile（底部切换键） | **14** |
| **back 后退** | **4** | wheelmode（滚轮模式键） | **106** |
| **forward 前进** | **5** | wheelup / wheeldown | 9 / 10 |
| tiltleft / tiltright | 52 / 53 | | |

> ⚠️ `forward=5`、`back=4`，**不是 90/91**。用错 ID 时设备返回 `FAIL`，
> 看起来像"命令不支持"，极易误判。

### 5.2 绑定功能表（fn）—— 实测（A）

读绑定 `0x02 0x8C`（size 10）：发送 `[profile, button, layer, 0×7]`，
响应 `[profile, button, layer, fn, fn_size, data(5)]`。
写绑定 `0x02 0x0C`，发送 `[profile, button, layer, fn, fn_size, data(5)]`。
`layer`：`0`=normal，`1`=hypershift。

| fn | 名称 | fn_size | data 布局 |
|---|---|---|---|
| `0` | off | 0 | — |
| `1` | 鼠标键 | 1 | `[mouse_code]` |
| **`2`** | **键 / 组合键** | **2** | **`[modifier_bits, usage]`** |
| `3` | 播放宏 | 3 | `[id_hi, id_lo, times]` |
| `4` | 按住播放宏 | 3 | `[id_hi, id_lo, 1]`（按住循环、松开即停） |
| `5` | 开关播放宏 | 3 | `[id_hi, id_lo, 1]`（点一次循环、再点停） |
| `6` | DPI 动作 | 1 | `[1 up / 2 down / 6 cycle]` |
| `7` | 下一槽 | 1 | `[0x04]` |
| `10` | 媒体键 | 2 | `[code_hi, code_lo]` |
| `11` | 双击 | 1 | `[1]` |
| `12` | Hypershift | 1 | `[1]` |
| `14` | 扩展鼠标动作 | 1 | `[mouse_code]` |
| `18` | 滚轮模式切换 | 1 | `[1]` |

修饰位（modifier_bits，A）：`0x01` ctrl、`0x02` shift、`0x04` alt、`0x08` win，
高位版 `0x10/0x20/0x40/0x80` 分别是右 ctrl/shift/alt/win。
实读 forward = `04 1A` → alt + w。

`mouse_code`（作为**动作**）：`1` left、`2` right、`3` middle、`4` back、`5` forward、
`9` wheelup、`10` wheeldown、`0x68` tiltleft、`0x69` tiltright。

> ⚠️ 三处极易错：
> 1. `fn=2` 才是键/组合键，`fn=3` 是宏。
> 2. data 顺序是 `[修饰位, 主键]`，不是反过来。
> 3. tilt 作**动作**是 `0x68/0x69`，作**按钮 ID** 是 `52/53`，两套编码不要混。
> 4. `fn=0x0E` 不是 openrazer 说的 turbo（长度 3），实测是本机的滚轮左右倾，长度 1，
>    设备不做归一化，按"扩展鼠标动作"处理（A）。

### 5.3 三种宏触发方式都是真实功能（A，物理验收）

`fn=3` 播放一次、`fn=4` 按住循环/松开停、`fn=5` 点一次循环/再点停。
三者都写进按键绑定、断电不丢，`tests/holdtest.py` 做过两轮真实按键观测，
GUI「按键映射」页据此开放三类编辑。

## 6. 宏

### 6.1 宏指令编码（A）

宏体是字节对序列：

| 字节 | 含义 | 示例 |
|---|---|---|
| `0x01, usage` | 按下键 | `01 06` = 按下 c |
| `0x02, usage` | 松开键 | `02 06` = 松开 c |
| `0x08, mask` | 鼠标键按下/松开 | `08 01` 左键按下，`08 00` 全松 |
| `0x0A, delta` | 滚轮 | `0A 01` 上滚一格 |
| `0x11, ms` | 延时 1 字节（≤255ms） | `11 78` = 120ms |
| `0x12, hi, lo` | 延时 2 字节大端 | `12 01 F4` = 500ms |
| `0x05, hi, lo` | 媒体键按下 | `05 00 CD` = 播放/暂停 |
| `0x06, 00, 00` | 媒体键松开 | — |

组合键顺序：先按修饰键 → 按主键 → 松主键 → **逆序**松修饰键。例 `ctrl+shift+r`：

```
01 E0  01 E1  01 15  02 15  02 E1  02 E0
lctrl  lshift  r      r      lshift lctrl
```

**文本只能发 HID usage 即 ASCII；中文无法直接输入。**

### 6.2 Flash 里的宏读写（cls `0x06`，A）

| 操作 | cmd | 说明 |
|---|---|---|
| 宏数量 | `0x80` | → `[count_hi, count_lo]` |
| 读宏大小 | `0x88` | 发 `[id_hi, id_lo, 0,0,0,0]` → `[id_hi, id_lo, len(4B BE)]` |
| 读宏内容 | `0x89` | 发 `[id, off(4B), len(1B)]`，数据从 offset 7 起，每块 ≤64B 循环拼 |
| 分配大小 | `0x08` | 发 `[id, len(4B BE)]` |
| 写宏内容 | `0x09` | 发 `[id, off(4B), chunk(1B), data...]`，块间 sleep ≥50ms |
| 删除宏 | `0x03` | 发 `[id_hi, id_lo]` |

> ⚠️ **不能覆写已存在的宏 ID**：`MACRO_SET_SIZE` 直接回 `Fail 0x06/0x08`，
> 必须先删除再写。`razer-core::macro_write` 已封装"备份 → 删 → 写 → 失败还原"。

设备只报宏总数、不报 ID 列表，所以 RazerMate 用 `macro_scan()` 逐 ID 探测，
结果记入本地登记表 `macros.conf`。

## 7. 灯效

### 7.1 三个可独立控制的灯区（region，A）

| 值 | 区域 |
|---|---|
| `0x01` | 滚轮 |
| `0x04` | Logo |
| `0x0A` | 底边灯条（11 颗） |
| `0x00` | **写 = 全部三区；读 = 无效** |

> ⚠️ 读灯效必须指定具体 region，用 `0x00` 读无效。

### 7.2 效果（A）

| effect | 效果 | 落盘 | 备注 |
|---|---|---|---|
| `1` | 静态色 | 是 | |
| `3` | 光谱循环 spectrum | 是 | mode=1 |
| `4` | 波浪 wave | 是 | mode=1 顺 / 2 逆，speed 0 最快～255 最慢 |
| `8` | 逐颗自定义 CUSTOM | **否** | 运行时；设备只回报 2 颗颜色，解析须按实际字节数 |

读灯效 `0x0F 0x82`（size 2，发 `[profile, region]`），
写 `0x0F 0x02`，读亮度 `0x0F 0x84`，写亮度 `0x0F 0x04`（pct 0..255，**用原始值不要按百分比换算**，
否则有损）。

> ⚠️ CUSTOM 灯效的 GET_EFFECT 应答 `data_size=0x0c`，`n` 字段写 11 但只给 2 颗颜色。
> 解析按实际字节数取，不要强求 `6+n×3`；解析失败要报 `Error::Parse`，
> 不要误报成 HID 传输失败。

### 7.3 软件动画的实测帧率（A）

逐颗 LED 连刷：**142.9 fps（7.00 ms/帧，11 颗灯）**，瓶颈是 HID 传输节奏而非协议解析。
30 fps 约需单核 21% 占用。因此本项目只把软件动画做成"预览"（彩虹/渐变/流动），
不常驻；长期效果一律用固件生成的板载光谱/波浪（零占用）。
预览前备份原灯效，点"还原"恢复；只在 `effect != CUSTOM` 时写备份，
否则会把临时彩虹色存成永久静态色（实测踩到过）。

## 8. 性能参数

### 8.1 DPI（cls `0x04`，A）

**注意 DPI 不在 `0x0B` 传感器类里**（扫 `0x0B 0x80..0x8F` 全无有效载荷），
而在 `0x04` 鼠标/传感器参数类。

| 操作 | cmd | size | 参数 / 响应 |
|---|---|---|---|
| 读 DPI | `0x85` | 7 | 发 profile → `[profile, x_hi, x_lo, y_hi, y_lo, 0, 0]` |
| 写 DPI | `0x05` | 7 | 发 `[profile, x, x, y, y, 0, 0]` |
| 读 DPI 档位 | `0x86` | 38 | `[profile, active_stage, count, 5×(idx,x,y)]` |
| 写 DPI 档位 | `0x06` | 38 | 同上结构 |

16 位大端。本机 slot 4 = 2700、slot 3 = 2300（A，切槽即变）。

> ⚠️ DPI 两条硬事实：
> 1. **normal mode 下写入静默失败**：返回 OK、不报错、值不变。必须切 driver mode 写。
> 2. **写入不落盘**：写 1800 → 切槽 → 回 2700。
>
> 正确流程：`读原模式/原槽 → 切 3 → 写 → 读回校验 → 切回原模式 → 还原原槽 → 失败回滚`。

### 8.2 回报率（cls `0x00`，A）

读 `0x8E`、写 `0x0E`，size 2。**存的是轮询间隔 delay_ms，不是 Hz**：
`Hz = 1000 / delay_ms`。设备只认 `1`（1000Hz）、`2`（500Hz）、`8`（125Hz）三档。
实测 `[04, 01]` → 1000Hz。回报率是**设备级**设置，不带 profile 参数
（与下面滚轮三项不同）。

### 8.3 滚轮三项（A）

| 操作 | 读 | 写 | 参数 |
|---|---|---|---|
| 滚轮模式 | `0x94` | `0x14` | `[profile, mode]`（0 段落 / 1 自由） |
| 滚轮加速 | `0x96` | `0x16` | `[profile, on]` |
| 智能卷动 | `0x97` | `0x17` | `[profile, on]` |

应答 `[profile, value]`：第一字节回显槽号，第二字节才是设定值。
**normal mode 即可写，无需 driver mode；按槽独立、跨切槽保持，p0 可独立寻址。**
本机 5 槽 + p0 基线：`mode=0 / accel=0 / smart=1`。

## 9. Flash 存储模型

```
总容量 90 KiB = 360 页 × 256 B
页状态：available ──写入──> used ──擦除──> recycled ──格式化──> available
```

查询 `0x06 0x8E`（size 14）→ `[unk(2), total(4), available(4), recycled(4)]` 全大端。
实测 total 92160、available 90368、recycled 2304 字节。

- `available` **包含** `recycled`；**立即可用 = available − recycled**。
- 设备**不会自动格式化**：删除数据只把页推进 `recycled`。
- 实测：写 24B 宏再删除 → available 少 256、recycled 多 256，**立即可用净少 512（2 页）**。
- 不提供擦写寿命计数。
- 新建宏只在 available 分配，满了会写失败；需格式化 + 重写全部数据（垃圾回收）。

> 本项目策略：**不做自动格式化**，虚拟槽走 p0 从根上避免写入。
> 格式化命令虽存在但未记录命令码，且属破坏性操作，**不在本项目自动化范围内**。

## 10. 报文格式与事务（实现者参考）

### 10.1 结构（90 字节）

```c
struct Report {
    u8  status;           // 发送恒 0x00
    u8  transaction_id;   // Basilisk V3 固定 0x1F
    u16 remaining_packets;// BE，恒 0
    u8  protocol_type;    // 0x00
    u8  data_size;
    u8  command_class;
    u8  command_id;
    u8  arguments[80];
    u8  crc;
    u8  reserved;         // 0x00
};
```

`HidD_SetFeature/GetFeature` 长度是 **91**：首字节 report id `0x00` + 90 字节结构体（B，
与 openrazer / razerqdhid 一致，本机可通信）。
**CRC = `bytes[2..88]` 异或，写入 `bytes[88]`**（B）。

### 10.2 三个易错语义

1. **`data_size` = 发送参数区长度，不是响应长度。** 响应中前 `data_size` 字节是应答数据，
   通常前缀是请求参数的回显。读命令的解析偏移 = 回显长度（A）。
   例：按键读取发 `[profile, button, layer, 0×7]` → 响应 `[profile, button, layer, fn, fn_size, data(5)]`。
2. **状态码**：0 NEW / 1 **BUSY（继续重试）** / 2 OK / 3 FAIL / 4 TIMEOUT / 5 NOT_SUPPORTED（B）。
3. **写后立刻读大概率返回 BUSY 或旧值**，必须等 ≥250ms 或走重试
   （最多 `15×(wait_power+1)` 次，第 i 次前睡 `10ms×(i+1)`，与 razerqdhid 一致）（A）。

### 10.3 事务流程

```
1. 组装报文、算 CRC、HidD_SetFeature(0x00 + 90B)
2. 循环 HidD_GetFeature(0x00, 91)，去首字节
3. 校验 response.class/id == request.class/id（不匹配 → 有别的程序抢设备，报错）
4. status OK → 返回；BUSY → 继续；其他 → 报错
```

命令类速查：`0x00` DEVICE、`0x02` BUTTON、`0x04` MOUSE(DPI)、`0x05` PROFILE、
`0x06` FLASH/MACRO、`0x0B` SENSOR、`0x0F` LED。

## 11. 已知坑清单（AI 必读，全部实测踩过）

| 坑 | 现象 | 对策 |
|---|---|---|
| 响应回显 | 返回前 N 字节是请求参数回显，数据在其后 | 按各命令固定偏移取 |
| BUSY | 写完立刻读返回失败/旧值 | 读带重试；写后 sleep ≥250ms |
| normal 写 DPI | **静默失败**：成功但不生效 | 切 driver 写，写完切回并还原槽 |
| driver mode | 板载宏与绑定全失效 | 只在写 DPI 窗口短暂切，用完立刻回 normal |
| 切 driver 再回 | 生效槽被重置为 1 | 记原槽并还原 |
| p0 | 切槽/断电即被覆盖 | 只当工作层，不当持久层，不跨切槽缓存 |
| 按键 ID | forward/back 不是 90/91 | 用 §5.1 表（4 / 5） |
| 宏 ID 解析 | `macro:0x0001` 的 `x` 被当乘号 | 先整体按十六进制 ID 解析，失败再拆 `xN` |
| 宏覆写 | 设备拒绝覆盖已存在 ID | 备份 → 删 → 写 → 失败还原 |
| 灯效读 region=0 | 无效 | 读必须指定具体区 |
| 亮度百分比 | 换算有损 | 用原始 0–255 值还原 |
| CUSTOM 读 | n=11 但只回 2 颗颜色 | 按实际字节数解析；区分 Parse 与 Io 错误 |
| 预览备份 | CUSTOM 态下备份会把临时色写成永久 | 只在 effect≠CUSTOM 时写备份 |

## 12. 术语表（给用户与 AI 对齐用词）

| 词 | 含义 |
|---|---|
| 槽 / profile / slot | 一套可切换的完整配置，1–5 在 Flash，0 是临时层 |
| p0 / direct profile | 当前生效配置的 RAM 工作副本，切槽/断电即丢失 |
| 模式 / mode | 设备解释按键的方式：normal(0) 固件自己 / driver(3) 软件接管 |
| 板载 | 存在鼠标 Flash 里、断电保留 |
| 绑定 / binding | 某个物理键在某个层上触发什么功能（fn + data） |
| fn | 绑定功能的类型编号（键、宏、DPI 动作等） |
| hypershift | 第二层按键映射，按住触发键时切换到 layer=1 |
| feature report | HID 控制传输的一种，本协议用 90 字节 payload |
| available / recycled | Flash 页状态；立即可用 = available − recycled |
